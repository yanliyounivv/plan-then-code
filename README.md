# my-dev-skills

**给 AI 编程助手的一套硬约束。管的是「计划之后」的那五件事。**

现在「先出计划再动手」已经是标配。真正每天出问题的是计划之后：规则打架听谁的、同一条错第三次还试不试、规则写到第 50 条会不会自相矛盾、AI 说「改好了」凭什么算过。这里每一件都有硬答案，而且能被脚本验。

> 一句话定位：**按计划写代码，不是按代码写 md。** 主产物是跑得起来的代码；文档在收尾时一次补齐，不拿它当进度证据。

安装方式：把 `skills/` 下两个目录放进 AI 工具的 skills 目录即可。不需要 API、不需要服务器。

---

## 它和常见的「计划模式」差在哪

| 情境 | 常见做法 | 这里的规定 |
|---|---|---|
| 规则打架 | 没有裁决，AI 挑对自己方便的那条执行 | 六级优先级 P0–P5 + 三条元规则，先判**是「顺序」还是「质量」**问题 |
| 连续失败 | 换个写法再试，试到通为止 | 同一条**失败 2 次必须停**下来汇报，禁止第 3 次盲试 |
| 规则与事实 | 规则说了算，代码不对是代码的问题 | 当轮**以实测为准**，收尾回头改规则并记进化日志 |
| 规则膨胀 | 越写越长，最后没人读完 | 单个 `SKILL.md` **≤ 7000 字节**，超了必须把细节下沉 |
| 规则质量 | 靠人读一遍，凭感觉觉得「挺全」 | **6 项脚本校验**（死链/结构/版本/体量/重复/卫生）+ 5 句冒烟用例 |
| 你的地位 | 规则可能反过来绑住你 | P0 = **你本次对话里的明确指令**，压过下面全部条款 |

## 四个反直觉的设计

1. **确认越多，越是在浪费你** —— 需求澄清并进出计划那条消息，确认门只留两道：出计划时一次，方案拍板时一次。
2. **失败两次就停，不许再试** —— AI 最贵的不是慢，是第 3、4、5 次盲试：看起来在努力，其实在烧你的时间和 token。
3. **规则不许压过事实** —— 规则和磁盘代码冲突时，当轮以实测为准，收尾回头改规则。规则是工具，不是用来赢辩论的。
4. **规则自己也要过 CI** —— 写规则必然会「说了 A 处、忘改 B 处」，所以带一个校验脚本，再带 5 句话验证规则到底有没有被加载。

## 里面有什么

```
.
├── skills/
│   ├── my-dev-workflow/        管顺序：整件事怎么推进
│   │   ├── SKILL.md            ⓪ 入口门禁 → ② 拍板拆 T1…Tn → ③ 逐条写 → ④ 审计 → ⑤ 验收 → ⑥ 上线
│   │   ├── references/         6 篇阶段 SOP + 决策树 · 日志 · 文件 · 流程图 · 交付形态
│   │   └── assets/             日志模板 · ADR 模板
│   └── my-dev-rules/           管质量：这一段怎么做才对
│       ├── SKILL.md            P0–P5 优先级 + 十六条铁律 R01–R16
│       └── references/         案例 · 协作流程 · 4 篇分端技术红线 · 产品体验 · 交付规范
├── 校验.sh                     六项检查：死链 / 结构 / 版本 / 体量 / 重复 / 卫生
├── 自检任务.md                 5 句冒烟用例：验证规则有没有被真正加载
├── skill工作原理.md            用 Mermaid 画清系统怎么运转
└── docs/                       宣传页与完整原理页（可直接开 GitHub Pages）
```

两个 skill 的触发域刻意不重叠：`description` 已按「推进节奏」与「代码质量」切开，避免一句话让两个 skill 各读一遍全文、白烧上下文。

**分工一句话**：工作流决定**顺序**，规则库决定**质量**。

## 安装

**支持 skills 目录机制的工具**（如 WorkBuddy / CodeBuddy 等）：

```bash
# 以用户级安装为例，路径按你的工具调整
cp -R skills/my-dev-rules skills/my-dev-workflow ~/.workbuddy/skills/
```

装完新开一个会话生效。

**不支持该机制的工具**：把 `SKILL.md` 贴进系统提示词，`references/` 里的内容按需再喂。效果会打折，但核心门禁还在。

## 验证装对了

开一个新会话，原样发下面五句，**只看它的第一个动作**是否停在门禁上：

| # | 发什么 | 期望的第一个动作 |
|---|---|---|
| S1 | `把登录页那个按钮颜色改一下，不好看` | 不写代码，先复述「哪个按钮」，出计划，等确认 |
| S2 | `帮我审计一下这个项目` | 立刻读磁盘代码，产出 P0–P3 清单，每条带 `文件:行号` |
| S3 | `继续往下做` | 直接取下一条 Tn 开工，说明这是第几条 |
| S4 | `报错了：NPM packages not found` | 先问「什么操作下出现的、哪个环境」，再动手 |
| S5 | `用户头像上传在个人页修好了` | 横向扫全项目同类，一次性汇报 |

任一条不符，说明该条规则没被真正加载——先查它是否位于 `SKILL.md` 的「必读」区，而不只躺在 `references/` 里（references 是按需加载，放在那里不会被每条任务读到）。

## 改规则

```bash
# 1. 改 skills/ 里的文件，同时改 frontmatter 的 version 与 updated
# 2. 跑校验，有 fail 先修
./校验.sh
```

硬预算：每个 `SKILL.md` ≤ 7000 字节。超了就说明该把细节下沉到 `references/`——`SKILL.md` 只放「每次都必须遵守」的内容。

版本号规则：改一句话 +0.1，重排章节/增删文件 +1.0；两个 skill 各自独立递增。
