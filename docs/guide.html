My Skill System · How It Works

这不是一堆提示词，而是一套约束 AI 行为的协作协议：任务到手先出计划、只确认一次， 然后拆成带编号的任务逐条写、逐条验、逐条报；文档不在编码途中补，而在任务完成时一次补齐。 一句话——按计划写代码，不是按代码写 md。

01

它解决什么问题

AI 写代码最常见的三种失控，这里各有一条对策

和 AI 协作写代码，翻车基本不在"写不出来"，而在三件事：理解错了就动手、边写边想越写越偏、做完了拿文档当证据。这套系统把这三件事各自钉在流程的一个位置上。

Problem 01

没理解就动手

对策：⓪ 入口门禁。先把理解复述一遍、圈定范围与验收点，只有一次确认，点头前一行代码都不写。

Problem 02

边写边想越写越偏

对策：② 把方案落成 T1…Tn，每条带「做什么 / 验收点 / 依赖」。③ 只按编号推进，验不过不进下一条。

Problem 03

拿文档当证据

对策：判进度、审计、排错一律看磁盘真实代码；交付必须给证据——接口实测、构建通过、或前后截图。

主产物是跑得起来的代码；计划是驱动代码的图纸；文档在任务完成时统一更新到位——该更的都更、该记的都记，但不边写边补，也不拿文档当进度证据。 —— my-dev-workflow 的一句话定位

能力黑名单（越界就不接）

只做：计划推进、按编号执行、交接上下文、日志与文件结构管理、流程图。
不做：纯问答 / 翻译 / 闲聊 · 排期报价与人力估算 · 代替用户决定涉钱、资质、合规、发布的事 · 没看到代码就给架构评审结论。

越界时只回两句话之一：「这归 X 管，不走本流程」或「要先看到代码（或截图、报错原文）才能判断」。

03

主线：一次任务怎么走

点开每一步看硬要求 · 全系统只有这一处画全套流程

  • 接任务先答三问，缺什么问什么，不拿"我以为"当输入。然后一次性给出计划与理解复述，等一句确认。

    • 三问：目标端（小程序 / Web 后台 / 后端 / 原生 App / 单文件）、代码范围（哪个项目哪个目录）、验收方式（截图 / 接口实测 / 构建通过）
    • 计划五件套：目标范围、阶段顺序、验收点、待确认点、风险
    • 用户说「先列需求 / 不改代码」→ 停在设计层，只出方案不写码
    W01R01一次确认

  • 给 2~3 个方案并附推荐，由用户拍板；随后把方案落成带编号的任务清单——这一步没做完就进③，等于边想边写。

    • 每条 Tn 必须写清：做什么 + 验收点 + 依赖，三缺一不算完成
    • 同时定契约（接口字段、状态枚举），后面五方对齐以它为准
    方案选项制契约单一来源纯设计到此为止

  • 只做当前编号的那一条，写完立刻在自己这里验证，然后把结果报出来；没过验收点不进下一条。

    • 同一条连续失败 2 次必须停下汇报，禁止第 3 次盲试
    • 动手这一刻去查规则库：这一段怎么写才对
    • 不打断去补文档；发现同类问题先记着，收尾一次汇报
    W02验一条报一条R06 R07

  • 审计只认磁盘代码与实测，文档只作线索。问题按 P0–P3 排序，每条都标到 文件:行号 这一级

    • P0 / P1 清零才允许进⑤
    • 修复循环里同一个问题最多 3 轮
    R02P0–P3最多 3 轮

  • 按交付规范的结构汇报：给证据、标级别、说清哪些还没做。

    • 证据三选一：接口实测 / 构建通过 / 截图对比
    • 功能分级：【真实现 / 占位 / 演示数据】，占位要留扩展点
    • 五方对齐：调用 ↔ 字段 ↔ 返回 ↔ 库 ↔ 后台
    R14 R15五方对齐R12

  • 上线前先跑清单、备好回滚路径；但部署、提审、开公网、重启、git 提交这些动作，一律等用户明确说。

    W05R16

  • 任务完成时一次补齐，不是只记一条流水：

    • 横向扫全项目同类问题，一次汇报（扫出来必须说，但只修本任务范围内 + 影响当前链路的）
    • 统一更新：开发日志 / 文件地图 / 契约 / 流程图 / ADR
    W04R03

小改动的计划已经足够明确时可直接进③；纯设计任务停在②。除此之外，确认门只有两处：⓪ 的计划、② 的拍板。

04

三处门禁与优先级

两套规则并存必然打架，所以必须有一处裁决顺序

优先级定义全系统只此一处。没有这一层，AI 会挑对自己方便的那条执行——这正是"文档一套、代码一套"的来源。

  • P0用户在本次对话里的明确指令 — 覆盖下面任何条款
  • P1安全与数据不可逆风险 — 宁可停手先问
  • P2编号铁律 R01–R16
  • P3流程阶段顺序 W01–W05
  • P4技术细则 — 分端红线、框架约定
  • P5案例库与历史经验

三条元规则（跨级冲突时用）

1 · 两个 skill 打架：先判是"顺序"还是"质量"——顺序听 workflow，质量听 rules；分不清取更保守的一方。

2 · 规则与磁盘代码冲突：当轮以实测为准，按真实代码办事，收尾回头改规则并记进化日志。规则不许压过事实。

3 · 同级冲突：先看是否触及不可逆伤害；再比范围——"修一处扫同类"不等于全改：扫出来必须一次汇报，但只修本任务范围内、影响当前链路的，跨模块列清单等拍板。

05

十六条铁律

违反即返工，可在日志与审计里按编号回指

⌕
R01

不许没理解就动手

模糊指令先复述理解，等确认再动手。

R02

不许只看文档不看代码

审计、进度、排查只认磁盘代码与实测。

R03

不许修一处不查同类

修完全项目扫同类，一次汇报一起修。

R04

不许重复索要已给信息

参数、截图、报错不再问第二遍。

R05

不许原地空想不行动

缺插件缺方案就自己去找去试。

R06

不许把占位当真实现

占位说占位，假数据说假数据。

R07

不许把环境噪音当缺陷

先判性质，不为误报改业务代码。

R08

不许启动完不验证

端口 + 健康检查 + 主链路；验不了要说验不了。

R09

不许拿"文件一致"当结论

md5 相同 ≠ 渲染正确，要查 CSS 层叠。

R10

无假数据

数据须入库、走真实链路；空就展示空状态。

R11

无死按钮、无断流程

按钮真调接口；发起→详情→流转→完成→可回看。

R12

前后端契约一致

调用↔字段↔返回↔库↔后台，五方对齐。

R13

状态全中文 + 全端共用

一张枚举映射表，不把 pending 透给用户。

R14

证据三选一必给

接口实测 / 构建通过 / 截图；UI 必须前后对比。

R15

功能分级标注

【真实现 / 占位 / 演示数据】，占位要留扩展点。

R16

部署提交等指令

部署、提审、开公网、重启、git 提交都等明确说。

没有匹配的铁律，换个关键词试试。

R01–R09 的真实翻车案例收在 references/最痛的教训.md；R10–R13 细则在 references/产品体验.md §4–§7；R14–R16 的结构与清单在 references/交付规范.md。

06

文件结构

源头只有一处，安装副本单向生成

My_Skill/ 是唯一权威源头，改规则只改这里。系统里那两个 my-dev-* 只是安装副本——直接改它们，源头会立刻变成过期快照。

My_Skill/
├── README.md                总索引 + 维护规则
├── 校验.sh                  守门人：六项检查（只读）
├── 自检任务.md              冒烟用例：5 句话验证是否生效
├── 进化日志.md              所有 skill 的更新记录
├── skill工作原理.md          系统工作原理图（Mermaid）
├── 同步工具.sh               check 查差 / pack 打包 / sync 安装
├── skills/                  唯一权威源头，改规则只改这里
│   ├── my-dev-rules/        规则库：这一段「怎么做才对」
│   │   └── references/      案例 · 协作流程 · 4 篇分端红线 · 产品体验 · 交付规范
│   └── my-dev-workflow/     工作流：整件事「怎么推进」
│       ├── references/      6 篇阶段 SOP + 决策树 · 日志 · 文件 · 流程图 · 交付形态
│       └── assets/          日志模板 · ADR 模板（模板唯一存放处）
└── skills安装包/            可分发的 zip（由 pack 生成，不手打）
07

维护闭环

规则不自动进化：只在明确要求改规则时才动，然后走这条链

STEP 01
改 skills/ 里的文件
同时改 frontmatter 的 version 与 updated，并记进化日志。
STEP 02
./校验.sh
六项：死链 / 结构完整性 / 版本 / 体量 / 重复 / 卫生。有 fail 回第一步。
STEP 03
check · pack · sync
查两边哪边新 → 重打 zip → 装到用户级（要输入「覆盖」）。
STEP 04
跑自检 5 句
新会话里发那 5 句，看过不了就回去改。两次都过才算稳。

方向是单向的：只能从 My_Skill/skills/ 单向流向用户级 skills 目录，反过来直接改安装副本会让源头变成过期快照——2026-11-24 就这么落后过一整个版本。check 就是为拦这个加的。

为什么加校验脚本：规则写多了必然"说了 A 处、忘改 B 处"。六项里最值钱的是重复段落和死链——它们正是单一事实源被破坏的两个征兆。

硬预算：每个 SKILL.md ≤ 7000 字节。超了就说明该把细节下沉到 references/；SKILL.md 只放"每次都必须遵守"的内容。

08

自检：5 句话验证

规则写得再漂亮，也可能因为触发词没收好而根本没被加载

改完 skill 后开新会话，把下面 5 句原样发过去，只看它的第一个动作——不是看答得好不好看，是看它有没有停在门禁上。
