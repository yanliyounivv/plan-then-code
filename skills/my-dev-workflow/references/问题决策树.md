# 问题决策树

## 遇到问题按序排查（别跳步）

```
遇到问题
 ├─ ① 复现 + 问清触发点（什么操作？哪个页面/按钮/环境？）
 │     能复现 → 继续；不能复现 → 补日志/埋点，禁止猜
 ├─ ② 看真实代码定位（不看文档、不凭记忆）
 │     分层：前端渲染 → 网络请求 → 后端逻辑 → 数据 → 环境
 ├─ ③ 查官方文档（版本/API/changelog/报错码）
 │     优先官方，标注来源与时间；价格/政策/版本必须联网
 ├─ ④ 搜现成插件/skill/MCP（不重复造轮子）
 │     有 → 用；无 → 自己写
 └─ ⑤ 最小修复（只改问题那一处，不顺手重构）
```

## 真实教训（为什么要这个顺序）

- E05：报错改了 4 次配置都不对，真因是手动点了"构建 npm"且项目零依赖——**没先问触发点**。
- E07：云端 Node 16 无全局 fetch，本地 Node 22 有——**没按目标环境判断**。
- E06：用旧训练数据答"云开发 19.9/月"，实际已有免费版——**价格政策没联网**。

## 问题分级（企业级缺陷管理）

| 级别 | 定义 | 处理时限 |
|---|---|---|
| P0 致命 | 数据丢失/资金错误/安全漏洞/主链路全断 | 立即修复，阻塞其他 |
| P1 高 | 核心功能不可用/必现 bug | 当日修复 |
| P2 中 | 次要功能/边界问题 | 排期修复 |
| P3 低 | 优化/坏味道/技术债 | 记录，择机 |

## 解决后收尾（先修代码，任务完成时统一留痕）

1. **横扫同类**（必做）：全项目搜同字段/组件/映射/模式，一次性汇报一起修。
2. **验证**（必做）：复跑原路径 + 回归相邻路径。
3. **任务完成时记日志**：P0/P1 问题在追踪表加一行（编号/级别/问题/根因/解决动作/状态），P2/P3 按需。
4. **任务完成时更新文件地图**（仅文件增删时）：改了文件结构才更新 `docs/00-项目总览.md`。

> 顺序是先修好代码、验证通过；文档统一在对话结束/任务完成时补齐。不允许为了填追踪表把修复拖住，也不允许收尾时漏掉该记的。
