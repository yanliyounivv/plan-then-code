# 阶段④ 审计复查 SOP

## 准入（Entry）

编码已完成，且 `03-编码实现.md` 的准出项全部满足，具体是这四条（代码层面，不看文档）：

- [ ] 构建 / 编译通过，贴出命令与输出
- [ ] 类型检查 / lint 无新增错误
- [ ] 本轮通过的验证命令有记录（接口实测、单测、页面截图三选一以上）
- [ ] 已知遗留项已列出，未把占位说成真实现

四条缺一条不进审计——否则审的是半成品，结论没有意义。

## 固定动作（按顺序）

1. **看真实代码**：证据基线只用磁盘代码 + 运行日志 + 实测命令，文档只作线索（`R02`）。
2. **契约三方对照**：前端调用 → 前端期望字段 → 后端实际返回。历史最致命问题全在这层。
3. **按 P0–P3 分级**：
   - P0 致命（数据 / 资金 / 安全 / 主链路）→ 立即修
   - P1 高（核心功能不可用）→ 当日修
   - P2 中（次要 / 边界）→ 排期修
   - P3 低（优化 / 坏味道）→ 记录择机
4. **修一处扫同类**：修完横向扫全项目同字段 / 组件 / 映射 / 模式，一次性汇报一起修（`R03`）。
   注意 `R03` 不等于全改：**扫出来必须一次汇报，但只修「本任务范围内」+「影响当前链路」的；跨模块的先列清单等用户拍板**（同级冲突裁决，见 `my-dev-rules` 规则优先级第 3 条）。
5. **修复轮次上限（硬规则）**：同一个问题**最多修 3 轮**。3 轮仍未解决 → 停手，输出「已排除项清单 + 三个可能根因 + 需要用户提供的信息（日志/复现步骤/环境）」，由用户决定继续还是换方向。
6. **回归验证**：修复后复跑同一套验证，证明修好且没引入新问题。

## 准出（DoD）

- [ ] 问题分级清单产出，每条带 `文件:行号` + 现象 + 根因
- [ ] P0 / P1 全部关闭
- [ ] 同类问题清零
- [ ] 修复有回归验证
- [ ] 环境噪音单独成节，并说明为何不改代码

## 收尾（任务完成时统一更新）

- 审计的主产物是**对话里的分级问题清单**，不是一份报告文件。
- 任务完成时：用户要归档的报告写 `docs/05-审计/`；P0/P1 在日志问题追踪表补一行，P2/P3 按需。
- 修的过程中增删了文件才更新文件地图。

## 触发口令

| 用户说 | 动作 |
|---|---|
| "检查一遍代码 / 看看结构健不健壮" | 全项目审计，出分级报告 |
| "看看有没有同类问题" | 横向扫描，一并修复 |
| "是不是只有这一个地方" | 直接做同类扫描，别只回答"是" |
