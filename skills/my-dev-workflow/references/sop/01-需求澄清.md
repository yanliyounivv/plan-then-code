# ⓪ 的追问清单（需求澄清）

> 定位：本文件是 **⓪ 入口门禁的细化动作**，不是独立阶段，**不单独设确认门**。
> 出计划时顺手把下面几问问掉，和计划一起**一次性**交给用户确认。需求清楚就跳过本文件。

## 何时展开

- 需求里有像素 / 位置 / 颜色 / 交互细节的描述
- 出现"错位""不对""不好看"这类主观词
- 涉及改多处、跨端、动数据结构

## 固定四步（串在 ⓪ 里，不额外要确认）

1. **复述理解**：一句话说清"我理解你要的是 X，方案是 Y，改动点在 Z"。
2. **追问易误解的三类描述**，先问清"是页面上的哪一块"：
   - 像素 / 位置 / 颜色——"去掉某块颜色"常指整块背景，不是改那个元素
   - "错位"——多半是 CSS 层叠，不是文件差异
   - "按钮不对"——可能是尺寸 / 间距 / 图标三件事之一
3. **圈定范围**：明确"改什么 / 不改什么"，写进 ⓪ 的计划里。
4. **并入 ⓪ 的那一次确认**：不要问"我理解对了吗"再问"计划可以吗"——合成一条，让用户一次点头。

## 产出

对齐后的理解 + 圈定的范围，直接带进 ② 拆任务，不单独写文档。
确实产出了需求文档时，任务完成时归档到 `docs/01-需求/`；没有就跳过。

## 触发口令

| 用户说 | 动作 |
|---|---|
| "先给我思路 / 你理解一下 / 先不动代码" | 只出理解 + 计划，不写代码 |
| "先列需求，不改代码" | 严格停在设计层，连代码片段都不给 |
| "继续 / 按这个来" | 不再复述，直接进 ② 或 ③ |
