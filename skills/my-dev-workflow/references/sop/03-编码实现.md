# 阶段③ 编码实现 SOP

> **这是整个 skill 的主战场。本阶段的主产物是代码，不是文档。** 严格按②确认的任务清单逐条推进：拿一条 → 写 → 验 → 报 → 下一条。

## 准入（Entry）
- 方案 + 任务清单（T1…Tn）已定稿；或用户明确说"按计划执行 / 继续往下做"。
- 计划不存在或含糊 → 退回②，不带着含糊计划写代码。

## 固定动作（按编号循环，逐条推进）

对清单里的每一条任务 Tn：

1. **认领**：说清"现在做 Tn：做什么、验收点是什么"，然后开写。
2. **写代码**：遵守 `my-dev-rules` 的技术红线——先读 `references/技术-通用红线.md`，再按端读 `技术-小程序与云开发.md` / `技术-Web与后端.md` / `技术-原生App与单文件.md` 中对应的那一篇：
   - 无假数据（测试数据必须有规律、入库、走真实链路）
   - 无死按钮、无断流程（发起→详情→流转→完成→可回看）
   - 前后端契约对齐（五方：调用↔字段↔返回↔库↔后台）
   - 状态全中文 + 全端共用（枚举映射表，单一来源）
3. **当场验证**：按该条的验收点跑验证（如 `node --check` / `npm test` / build / 接口实测），**没过不进下一条**。
4. **当场汇报**：一条完成立刻报一句——"Tn 完成：改了什么 / 验证结果 / 下一条是 Tn+1"。不憋大招，不等全部做完才说。
5. **卡住就报**：某条推进不了，明说卡在哪、已排除了什么、下一步试什么，不沉默跑长循环。
6. **失败上限（硬规则）**：同一条 `Tn` 的**同一个验收点连续失败 2 次**，必须停下来汇报——说清试过什么、两次报错差在哪、需要的判断是什么。**禁止第 3 次盲试**（改参数、换写法、删配置都属于盲试）。
   - 例外：用户明确说"再试一次 / 继续试"→ 可继续，但要先说清这次换的是什么思路，不能重复同一手法。
   - 这条是为了防"改十轮最后靠猜通了"，那种"通了"不算完成，因为根因没定位。

## 准出（DoD）
- [ ] 清单里每条 Tn 都有对应实现，且各自的验收点都验证通过
- [ ] 无假数据、无死按钮
- [ ] 契约对齐、状态文案中文且单一来源
- [ ] 发现的同类问题已横向扫过、一次性修完

> 准出看的是**代码状态**，不是文档是否补齐。

## 收尾（文档在任务完成时统一更新）
- 编码过程中靠逐条汇报保持透明，不边写边补文档；单条任务写完不记日志。
- **任务完成时**按 `日志规范.md` 统一更新：日志补记编码阶段流水、文件地图（有增删/改用途时）、契约文档与流程图（状态机/接口有变动时）、ADR（有不可逆决策时）——该更的必须更，不许只记一行流水。
- 没发生变更的项不动，不为凑数制造文档。

## 触发口令
| 用户说 | 动作 |
|---|---|
| "按计划逐条改 / 继续往下做 / 按编号执行" | 直接拿清单下一条开写 |
| "你自己看着搞" | 可自决，但事后说明选了什么、为什么 |
| "先列需求 / 先设计 / 不改代码" | 停在本阶段之外，只做设计 |
