# 技术通用红线（任何端写代码前先读这个）

> 这一篇是所有技术栈通用的底线。语言/端的专属坑见同目录另外三篇：
> `技术-小程序与云开发.md` / `技术-Web与后端.md` / `技术-原生App与单文件.md`

## 通用工程红线（所有语言/端都适用）

1. **契约单一来源**：状态枚举、错误码、权限点、金额单位、接口字段名各只有一处定义。最严重的 bug 全是"枚举双写 + 字段各写一份"。
2. **校验在服务端**：前端校验只是体验，后端必须独立校验角色、时间窗、状态前置、归属关系。只在前端禁用按钮 = 接口可被绕过。
3. **状态机集中**：流转走一张表（from → to → 角色 → 副作用），非法流转直接拒绝；不在业务里散写 `if`。
4. **金额**：统一整数分存储，展示层转元；禁止浮点累加；数量与金额用不同换算函数（用 `yuanToFen` 换算数量会把小数判成非法）。
5. **分页**：所有列表服务端分页并带上限，禁止"一次拉 5000 条再前端切"。
6. **幂等与并发**：写操作前端加 `submitting` 防重，后端加幂等键或唯一约束；扣库存/抢名额用事务或锁，并做并发验证（多线程抢最后一份只能 1 个成功）。
7. **非原子两步要补偿**：先改状态再建单必须事务或补偿任务 + 失败标记，否则出现"有意向无订单"。
8. **业务 ID 用序列**：`count()+1` 并发必撞号，用 Sequence/自增/雪花 ID。
9. **时间**：服务端生成时间戳，统一时区（云端统一校 UTC+8），展示层格式化中文；倒计时以服务端截止时间为基准。
10. **审计日志**：管理端每个写接口记操作人/对象/旧值/新值；配置类必须留痕，日志不可删。
11. **"只停不启 / 只写不读"都是缺陷**：轮询 `onHide` 必须配 `onShow` 重启；写了历史记录就要有读取入口；写了计数就要有展示。
12. **日志分级**：错误日志带 request_id / 用户 / 入参摘要；不打印密钥、token、完整手机号。

## 架构与选型

- **选型不预设答案**：每次开工前联网查证「当下哪个最好、最稳定、使用人数最多」，结合"个人开发者 + B 端小流量"前提（先算长期运维成本，再算开发成本），给 2~3 个候选让用户拍板，不写死某个具体技术。
- 配置链路闭环：后台保存 → 云端读取 → 前端生效，三段逐一实测。
- 每个管理接口进权限映射 + 写审计日志（配置类记旧值/新值）；幂等操作重复调用要拦截。
- 表设计先定状态机再建表；迁移脚本可回滚。

## 安全

- 密钥/AppSecret/令牌不进前端、不进仓库、不进日志（用户会在对话里发 key，配置时只写进配置文件/env，并提醒用户不要在聊天明文发送）。
- `.gitignore` 覆盖 `.env*`、`*.bak-*`、本地凭证；`cloudbaserc.json` 之类含凭据的配置不入库。
- 默认账号密码上线前必改；交付时提供后台测试账号密码清单。
- 演示数据、测试痕迹上线前逐条清理。

## 数据与并发

- 扣库存、抢名额必须事务或分布式锁，做到不超卖（8 线程抢 1 本库存，只有 1 个成功）。
- 关键写操作加唯一约束兜底，不只靠应用层判断。
- 列表一律服务端分页。
- 时间字段统一时区，展示层格式化中文。
- 慢查询先看执行计划再改，不盲目加缓存。

## 环境差异与占位符守护

- 本地能跑 ≠ 目标运行时能跑（真实事故：云端 Node 16 无全局 `fetch`，本地 Node 22 通过，线上登录 500）。
- 占位符（域名/环境 ID/密钥）未替换时必须有守护：检测到未配置就停发请求并给一次性明确提示，不许把 `INVALID_ENV` 抛给用户。
- 演示开关、开发默认开关、测试域名上线前逐条清理或确认保留。

## 验证闭环

- **验证不了就说验证不了，不许假装验过**。环境缺依赖（没装 node/npm、数据库连不上、没有真机）时，把结论降级为【未验证 · 原因】并给替代证据（静态检查、代码走查、逻辑推演），**不许写"已验证"**。`R08` 要的是"验证过或说明为何没验"，不是"必须构建成功"。
- **环境状态类事实必须带时间戳**：写"端口无监听/服务未启动/进程不在"等易变状态进文档或汇报前，必须标注测量时刻，并在交付前复测一次。真实事故：02:56 测 15721 无监听（用户 02:40 退出了 GUI），03:15 复测已在监听（03:00 重启），未标时间戳的快照被写进设计总集当结论，返工修正 6 处 + 一篇 ADR。
- 前端：构建通过 + 浏览器/真机实跑 + 截图对比（改前/改后各一张）。
- 后端：单测/自测全绿 + 接口实测（贴请求与响应）+ 重启后复测。
- 契约：至少一条"前端按真实调用 → 校验返回字段结构"的联调用例。
- 数据：测试用独立库/独立 Redis，用例自清理，跑完确认无残留。
- 多端：三端都跑起来走一遍主链路。
- 云上：部署后用真实请求 + 云端日志验证，不能只看 CLI 返回成功。

## 迁移 / 复刻 / 重构专项

- **视图层原样复制，只改数据层**。迁移/复刻时 WXML/WXSS/组件/全局样式/图片字体资源应逐字节保留，只替换请求层与类型适配。
- 迁移后做文件级对齐（`md5`/`diff` 统计差异数），把必须改的限定在数据层文件，并列出差异清单。
- **文件字节一致 ≠ 渲染正确**：错位查 CSS 层叠/覆盖/布局机制（如 `.btn` 的 `inline-flex` 被 `display:block` 覆盖导致图标占行、文字偏出）。
- 迁移期头号风险是**契约漂移**：前端按旧后端结构写死，新后端改简化结构后没同步 → 详情/列表/发布/导出/审核全坏。迁移完成必须做契约三方对照。
- 历史业务数据可以不迁，但**系统基础配置必须重新 seed**（字典、地区、角色权限、管理员、系统配置、消息模板、功能开关）。
- 换技术栈先算长期运维成本；目录策略一次定清：旧代码归档 `archive/` 保留 API 对照，新代码原位重建。
- 操作卫生：`cp -R 源 已存在目标` 产生嵌套（`cp/components/components`），先建空目录或 `rsync`；软链 `node_modules` 做完类型检查必须删；复制后核对扩展名（42 页应全 `.ts`，0 个 `.js`）。
